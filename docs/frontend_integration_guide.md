# "在吗" APP - 前端接入指南 (V1.0)

欢迎来到 "在吗" APP 前端接入指南！本文档旨在帮助客户端（iOS/Android/Web/小程序）开发者快速、规范地接入后端 V1.0 API。

## 1. 基础配置与环境

*   **Base URL (REST)**: `http://<服务器IP或域名>:8080/api/v1`
*   **Base URL (WebSocket)**: `ws://<服务器IP或域名>:8080/api/v1/ws`
*   **数据格式**: 所有 REST API 请求体和响应体均使用 `application/json`。

### 1.1 统一的响应结构
所有 REST API 均返回标准化的 JSON 结构：
```json
{
  "code": 0,          // 业务状态码：0 为成功，非 0 代表失败
  "message": "success", // 面向开发者的提示信息（或错误原因）
  "data": { ... }      // 业务数据，失败时通常为 null
}
```
**通用错误码处理建议**：
*   `code == 401`: Token 无效或已过期。前端应拦截此错误，清除本地存储的 Token，并强制跳转到登录页面。
*   `code != 0 && code != 401`: 业务逻辑错误（如参数错误、权限不足等），直接将 `message` 字段的内容通过 Toast 提示给用户即可。

## 2. 核心业务流接入指南

### 2.1 鉴权与登录流 (Auth)

本应用采用 **短信验证码 + JWT** 鉴权机制。所有鉴权以外的操作均需在 HTTP 头部携带 Token。

**步骤**：
1.  **请求验证码**：调用 `POST /auth/sms-code`。
    *(注意：开发环境下验证码不会真发短信，而是直接在接口的 `data` 中返回，请查阅控制台或接口返回值。)*
2.  **执行登录/注册**：调用 `POST /auth/login`，传入手机号、验证码和角色身份 (`role`: 1-长辈, 2-晚辈)。建议同时传入 `device_id`。
3.  **持久化 Token**：从响应中提取 `data.token`，并将其持久化到本地存储（如 SharedPreferences / NSUserDefaults / LocalStorage）。
4.  **全局拦截器**：配置 HTTP 客户端请求拦截器，在后续所有请求 Header 中自动注入：
    `Authorization: Bearer <填入你的Token>`

### 2.2 亲子绑定流 (Binding)

此流程是应用正常运转的基础，必须在一端发起，另一端确认。

1.  **查询绑定状态**：前端可在获取个人资料 `GET /user/profile` 时，检查返回的 `relations` 列表，或判断当前用户是否已绑定。
2.  **发起绑定 (长辈/晚辈均可发起)**：调用 `POST /user/bind`，输入对方的手机号并发起请求。此时后端会生成一条状态为 `pending` 的记录。
    *(此时可以给对方发一条短信或微信，提示对方登录 APP 进行确认。)*
3.  **确认绑定 (接收方操作)**：对方登录 APP 后，应能看到待确认的请求。调用 `POST /user/bind/confirm` 传入 `relation_id`。
4.  **注意**：接口已做幂等处理，重复发起或重复确认会返回相应的业务错误码（如 `1009/1010`），前端可直接 Toast 提示。

### 2.3 消息与聊天模块 (WebSocket + REST)

聊天是本应用最核心、最复杂的模块。请严格遵循这套 **推拉结合** 的策略：

1.  **建立连接**：应用切入前台、或用户登录成功后，立刻连接 WebSocket: `ws://.../ws?token=<你的Token>`。
2.  **心跳保活 (Ping)**：**极其重要**！前端需开启定时器，每 30 秒向服务器发一个业务层的心跳帧（或标准的 WS Ping 帧），否则 60 秒后服务端会强行断开连接。
3.  **断线重连与消息补偿 (Resync)**：
    由于移动网络不稳定，WS 必然会断开。当 WS 重新连接成功后，**千万不要仅仅依赖 WS 收消息**！
    *   **动作**：立刻调用 `GET /chat/history?peer_id=xxx&since_id=<本地最大消息ID>`。
    *   **目的**：把断网期间遗漏的所有消息一次性拉回来，存入本地 SQLite，然后刷新 UI。
4.  **发送与 ACK 机制**：
    *   前端构建消息并赋予一个本地伪随机 `temp_id`（如 UUID），随后发送给服务端，并在 UI 上显示“转圈/发送中”。
    *   收到服务器回传的 `{"type":"ack", "temp_id":"...", "message_id": 123}` 后，将该消息状态标为发送成功，并以服务器下发的 `message_id` 为准。
5.  **已读回执**：在聊天界面渲染了别人发来的新消息后，通过 WS 发生一个 `ack` 帧，告诉服务器此条消息已读。
    *(详细 JSON 结构请参考 `websocket_protocol.md`)*

### 2.4 设备监控数据上报 (Device)

此功能主要运行在**长辈端**的后台。

*   **数据打点**：长辈端 APP 需要在合适时机（如切换到后台、或定时任务触发时）采集当天的电量、步数、屏幕使用时间等信息。
*   **定时上报**：调用 `POST /device/upload` 将当天的汇总数据覆盖上传给服务器。后端会负责按照日期 (`record_date`) 建立唯一记录，多次上传会自动更新当天的最新数值。
*   **年轻端拉取**：年轻端进入首页时，调用 `/device/daily-insight` 拉取今日长辈状态及 AI 自动生成的关切提示卡片。

### 2.5 媒体上传规范 (SSRF 防御拦截)

后端在 R2 修复中启用了严格的 **SSRF (服务器端请求伪造) 拦截防御**。
当你在以下接口提交 URL 发给后端时：
1.  修改头像 (`PUT /user/profile` 的 `avatar_url`)
2.  发布广场气泡 (`POST /square/publish` 的 `voice_url`)
3.  语音转文字识音 (`POST /chat/stt` 的 `voice_url`)

**注意**：后端目前只允许 **HTTPS** 且以 **指定的 OSS 域名** (如 `.oss.aliyuncs.com`) 结尾的合法防跨站链接。请确保前端上传文件到真实 OSS 后，再将标准的 HTTPS 链接提交给后端 API，不要使用内网 IP (`192.168.x` / `10.x.x`) 或无域名的 HTTP 链接 测试，否则会被 API 拒绝请求。

## 3. 最佳实践与建议

1.  **防抖处理**：对于表单提交、消息发送、确认匹配等接口，前端务必做好按钮防抖过滤，避免用户快速连点导致向后端发出并发事务从而引发报错。
2.  **缓存策略**：对于不经常变化的接口（如获取用户信息、获取历史聊天列表等），请合理使用本地 SQLite 或内存缓存，避免频繁跨屏引发的不必要网络加载。天气与新闻接口在后端已有长达数小时的 Redis 逻辑缓存，并发调用无压力。
3.  **WebSocket 容错处理**：一定要实现指数退避重连（Exponential Backoff）。如果断开，不要立刻不停地死循环重连，应该延迟 1s, 2s, 4s, 8s 重连，以免服务器瞬间遭遇雪崩。
